기준은 앱 **v1.75 / build-76**과 공개 웹판 **build-76**이다. 오늘 개발 범위는 build-66부터 build-76까지다. build-65는 비교 기준이다. 이 문서는 Claude가 다음 작업을 시작할 때 볼 기록이다. 화면 코드와 APK·AAB·웹 HTML을 새로 빌드하는 작업은 이 인수인계에 포함되지 않는다.

## 유속 알고리즘과 그리는 코드

- **예보 입력과 확대 일관성.** `forecastPatch`는 경위도 0.1°로 정해진 입력 블록 `p66_…`을 선택한다. `realAt`은 현재 ROMS 회차를 확인한다. `interpAt`은 삼각형 내부에서 선형 벡터 보간, 바깥에서 반경 안의 매끄러운 거리 가중치를 사용한다. 동·북 성분을 시간 보간했다가 유속과 방위를 계산한다. 계기판·입질·그래프의 내부 값은 노트 기준을 사용하고, 표시 단위는 설정의 m/s·km/h·노트로 변환한다. [앱 코드](../app/src/main/assets/index.html)
- **항내 추정.** 남해에서 한 셀이 약 47m인 고정 `FIELD_LEVEL=15` 격자를 쓴다. `simViewTiles`는 화면 중심에 가까운 구역 최대 36개를 잡고 조작이 멈춘 뒤 약 1초에 계산을 예약한다. OSM 판별과 수심 마찰, ROMS 경계값을 받아 기존 격자 볼츠만 워커에서 계산한다. 결과 키는 `v68|구역|예보 시각|경계값 해시`다. 같은 시각·회차·입력의 완료 결과를 읽고, 계산 대기 벡터가 화면에서 반대로 잠깐 나타나는 동작을 막는다. 장애물이 없는 구역 등 `skip` 상태는 기본 예보를 읽는다. [앱 코드](../app/src/main/assets/index.html)
- **경계 보간.** `currentAtWorld`는 고정된 소유 구역과 이웃 구역을 동일한 지리 좌표 기준으로 찾는다. 겹치는 부분의 가중치는 `u²(3−2u)`이며 각 타일 안에서는 셀 중심을 기준으로 보간한다. 육지와 모서리로만 닿는 물 셀은 제외한다. 결과 승인에는 시각·지문·회차를 확인한다. [경계 시험](../test/qa_current_seam.js)
- **보라색 조류예보 지점.** `anchorCells`는 연결된 바다 셀을 4방향으로 따라 최대 600m까지 지나며 `(1−u)^4(4u+1)`로 영향력을 줄인다. `stationForcing`은 목표 벡터를 합쳐 워커에 완만한 보정으로 전달하고 `bcHash`에 포함한다. 보라색 마커는 해당 지점 예보를 보여준다. `diagCurrentLine`은 선택 지점과 보라색 지점에서 흐름 방향 기준 −250m·0m·+250m의 기본 예보·항내 추정, 격자와 육지 여부를 출력한다. [보정 시험](../test/qa_current_forcing.js)
- **흐름선의 움직임.** `flowDistance`는 1m/s당 초당 16 CSS px로 화면을 움직이고, `stepFlow`는 프레임 시간 차를 적용한다. 이는 화면 표현 설정이다. 화면 배율과 분리된 실제 예보 벡터는 `flowAt`, 화면 입자는 `flowDraw`에서 읽는다. [유향·표시 시험](../test/qa_b56.py)
- **잔상과 회색 면.** build-74는 배율이 바뀔 때 이전 픽셀 복사를 막았다. build-75는 동일 화면의 8비트 알파 합성이 남긴 희미한 픽셀을 30·60·120Hz에서 재현했고, `flowTrailContext`로 최근 250ms와 이전 250ms를 따로 그려 최대 약 500ms에 이전 픽셀을 지운다. 만료는 이동·바다 판별 대기 중에도 진행된다. build-76은 전체 흐름선 불투명도를 일반 .68, 밤낚시 .54로 제한했다. 입자 수는 `min(1200, W×H/320)`, 굵기는 저속 1px·그 밖 1.25px로 배율 확정 후 일정하다. 자료가 부족한 선은 1px와 `1−exp(−5×dt)` 합성을 쓰고, 약한 물살의 색을 파랑·청록 계열로 조정했다. 빠른 물살의 노랑·주황·빨강 색과 유속 기준값은 기존 기준을 쓴다. [앱 코드](../app/src/main/assets/index.html)

## 구현 판단과 근거

| 결정 | 선택한 이유와 확인할 점 |
|---|---|
| 같은 위치의 유향을 고정 격자와 예보 회차에 묶었다 | 사용자가 가장 우려한 것은 같은 시각의 같은 바다에서 확대·이동만으로 물살 방향이 잠깐 뒤집혀 앱을 신뢰하기 어려워지는 일이었다. 화면 배율과 무관하게 같은 입력을 선택하고, 완료된 결과만 표시하면 그 변동을 줄일 수 있다. 모의 시험에서는 고정 좌표의 벡터가 일치했다. 이 시험이 검증하는 범위는 화면 조작에 대한 일관성이고, 현장의 예보 정확도는 실측 대조가 필요하다. |
| 연결된 물 셀에서 유속 벡터를 보간하고 지점 예보의 영향력을 줄였다 | 계산 구역마다 경계에서 값을 갑자기 바꾸면 화면에 격자 모양의 급격한 경계가 생긴다. 인접 구역의 동·북 성분을 점진적으로 섞되, 방파제로 나뉜 물길은 각각의 흐름을 유지하도록 육지와 연결되지 않은 셀을 제외했다. 600m 보정은 기존 모델 안의 설정값이며 현장 검증이 남아 있다. 항구 입구의 흐름 차이는 실제 구조물·수심으로도 생길 수 있으므로, 진단값과 관측을 대조해 보간 문제와 구분해야 한다. |
| 배율 변경 잔상과 고정 화면의 회색 누적을 두 번에 걸쳐 고쳤다 | 먼저 확대 직후 이전 배율의 그림이 커져 남는 문제를 해결했다. 이후 사용자 화면을 계기로 배율을 고정한 시험에서 60Hz로 10초간 감쇠해도 반올림 때문에 희미한 픽셀이 남는 것을 재현했다. 시간 기준으로 오래된 버퍼를 비우면 남은 픽셀의 수명을 제한할 수 있다. 이어서 바다 위가 계속 뿌옇다는 피드백에 맞춰 선의 굵기·밀도·색·불투명도를 조정했다. 같은 모의 화면에서 밝게 덮이는 면적은 이전의 절반 이하였고, 현장 위성지도에서의 체감은 확인이 남아 있다. |
| 흐름선 움직임과 예보 유속을 따로 다뤘다 | 전자는 사용자가 물살을 읽는 데 드는 시간과 화면 가독성을 좌우하고, 후자는 낚시 판단에 쓰이는 값이다. 화면 움직임을 프레임 시간 기준으로 계산하면 주사율이 달라도 비슷하게 보인다. 다음 업데이트에서 확대할수록 선을 가늘게 하더라도 같은 위치·시각의 유속·유향과 화면 재생 속도를 각각 확인해야 한다. 넓은 화면의 굵기 수치는 흐름이 읽히면서 바다가 다시 뿌옇게 덮이지 않는 수준을 실기기에서 비교한 뒤 확정할 항목이다. |
| 추천 대상 어종과 실제 월별 조과를 나눴다 | 사용자는 예시처럼 처음 가는 항구나 방파제에서 무엇을 노려볼지 알고 싶어 했다. 추천 자료는 탐색 후보로 제공하고, 장소·시기·어종이 함께 확인되는 기록은 월별 조과로 표시했다. 게시일과 출조일이 다르면 확인 가능한 어획 월을 우선한다. 선상 조과를 출항항 방파제의 도보 조과로 귀속하면 장소에 대한 오해가 생긴다. 좌표가 주변 범위 수준이면 ‘주변 위치’로 표시하고 출처는 저장소에 둔다. |
| 다음 묶음에서 유향 일관성, 경계, 첫 화면 가독성, 핀 순으로 점검한다 | 방향이 뒤집히는 문제는 앱의 핵심인 유속 정보의 신뢰도에 직접 영향을 준다. 사각형과 급격한 경계는 원인 레이어와 데이터 출처를 확인하면 수정 범위를 잡을 수 있다. 첫 화면 표시와 핀 밀도는 그다음에 비교할 가독성 항목이다. 넓게 볼 때 굵고 확대할수록 가늘어져야 한다는 요구는 사용자 확인 사항이며, 나머지 점검 항목은 검토 후보로 남겼다. |

## 재현과 배포 위치

- 브라우저 시험은 저장소의 `test/tools/mkqa.py`로 시험 페이지를 만들고 `test/mock_roms_real.js`와 로컬 HTTP에서 `test/qa_b56.py`, `test/qa_b69.py`, `test/qa_flow.py`를 돌린다. 계산 경계와 보정 단위시험은 `node test/qa_current_seam.js`, `node test/qa_current_forcing.js`를 사용한다. 자동 시험은 모의 응답이라는 범위를 유지한다.
